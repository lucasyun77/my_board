# ysb 기획 — 기획서 먼저, 만들기는 나중에

> 출처: 애디 오스마니의 공개 스킬 묶음 중 「기획서 주도 개발」을 회장 현황판용으로 줄이고 한국어로 다시 쓴 것. 원본 허가문은 같은 폴더의 `원본-허가문.txt`.

## 핵심
코드를 쓰기 전에 **무엇을, 왜, 어디까지 만들고, 다 됐는지 어떻게 아는지**를 한 장에 적어 회장님과 맞춘다. 기획서 없이 만드는 것은 짐작이다.

## 반드시 지킬 것 (저장소 지침 우선)
- 기획서, 요약, 질문은 **모두 한국어**로 쓴다. 영어 단어·약어·파일 이름은 회장님께 드리는 글에 쓰지 않는다.
- 화면 그림이나 구성도는 **아티팩트 페이지**로 띄워 링크를 드린다. 그림 속 숫자가 예시이면 "예시"라고 적는다.
- 원하신 방식대로 만들 수 없는 것(실제 연동이 안 됨, 목업으로 흉내 냄 등)은 기획서와 답변 맨 앞에 **「⛔ 주의 — 의도대로 안 됨」** 상자로 먼저 알리고, 대안 후보를 드려 고르시게 한다.
- `docs/MODULES.md`의 공통 규칙을 따른다: 입력해서 찾는 선택칸, 화면 안 2단계 확인, 측정/수기/추정/미확인 배지, 휴대폰 폭, 다크모드. 숫자를 지어내지 않고, 연봉·임금은 넣지 않는다.

## 0단계: 범위 점검 (여러 기능이 묶였을 때만)
요청 하나에 따로 떼어 만들고 시험할 수 있는 기능이 여럿 섞여 있으면, 기획서보다 **기능 지도**를 먼저 드린다. 예를 들어 지시 등록, 아사나 연동, 이행률 보고가 한 요청에 들어 있는 경우다. 기능이 하나뿐이면 이 단계는 건너뛴다.

```
# 기능 지도: [이름]
| 기능 | 하는 일 | 먼저 있어야 하는 것 |
|---|---|---|
| 지시 등록 | 지시 입력·저장 | — |
| 아사나 연동 | 등록된 지시를 아사나로 | 지시 등록 |
만드는 순서: 지시 등록 → 아사나 연동
```
회장님이 지도를 승인하신 다음에 기능별로 1단계부터 진행한다.

## 1단계: 기획서 쓰기

**먼저 가정을 드러낸다.** 기획서 본문을 쓰기 전에, 짐작으로 채운 것을 번호를 매겨 보여 드린다.
```
제가 짐작한 것:
1. 회장님 전용 화면이며 직원에게는 보이지 않는다
2. 데이터는 지금은 샘플이고, 실제 연결은 다음 판에서 한다
3. 휴대폰에서도 본다
→ 틀린 것이 있으면 지금 고쳐 주세요.
```
모호한 부분을 조용히 메우지 않는다. 기획서를 쓰는 목적은 코드를 쓰기 전에 오해를 드러내는 것이다.

**"좋게 해 줘" 같은 말은 확인할 수 있는 조건으로 바꾼다.**
```
요청: "지시 화면을 보기 편하게"
완료 조건으로 바꾸면:
- 휴대폰에서 지시 10건이 가로 스크롤 없이 보인다
- 기한이 지난 지시가 맨 위에 빨간 표시로 보인다
→ 이 기준이 맞습니까?
```

**기획서 양식** (`docs/기획/<날짜>-<짧은이름>.md`로 저장한다. 작은 메뉴는 반 장이어도 된다.)
```markdown
# 기획서: [이름] — 1판

## 목적
무엇을 왜 만드는지, 누가 쓰는지, 무엇이 되면 성공인지.

## 화면 구성
화면 단위로 무엇이 보이고 무엇을 누를 수 있는지. 그림은 아티팩트 링크로 붙인다.

## 데이터와 출처
화면의 숫자와 목록이 어디서 오는지. 각 항목에 측정/수기/추정/미확인 중 하나를 표시한다. 목업으로 대신하는 것은 따로 적는다.

## 다른 메뉴와의 관계
어느 메뉴의 결과를 받아 쓰고, 어느 메뉴로 넘기는지.

## 지켜야 할 선
- 늘 한다: …
- 먼저 묻는다: 공용 파일 수정, 외부 발송(슬랙·아사나 실제 전송), 새 외부 도구 추가 …
- 하지 않는다: 숫자 지어내기, 연봉·임금 표시, 본 갈래에 바로 합치기 …

## 완료 조건
다 됐는지 확인할 수 있는 구체적인 조건.

## 이번 판에서 뺀 것 (다음 판 후보)
한 줄씩: 무엇을, 왜 미루는지.

## 남은 질문
회장님이 정해 주셔야 할 것.

## 만드는 쪽 참고
고칠 파일, 확인 방법(브라우저로 열어 화면 캡처 확인 등). 회장님께 드리는 요약에는 넣지 않는다.
```

**기획서를 쓴 뒤에는 반드시 멈춘다.**
1. 기획서를 저장하고 화면 그림 아티팩트 링크를 드린다.
2. 다섯 줄 안으로 요약하고, 남은 질문을 번호로 정리한다.
3. 「이대로 진행할까요, 고칠 곳이 있을까요?」라고 묻고 **그 차례를 끝낸다.** 같은 차례 안에서 계획을 세우거나 코드를 쓰지 않는다.

## 2단계 이후
회장님이 승인하시면 「ysb 계획」(`ysb-plan`) 스킬로 작업을 쪼갠다.

## 기획서는 살아 있는 문서
- 결정이 바뀌면 기획서를 먼저 고치고 그다음에 만든다.
- 만드는 도중에 떠오른 좋은 생각은 기획서 본문에 넣지 않는다. 「이번 판에서 뺀 것」에 적어 두고 하던 일을 계속한다.
- 이미 만든 메뉴를 바꿀 때는 원래 기획서를 바로 고치지 않는다. **변경 기획서**(`docs/기획/<날짜>-<이름>-변경.md`)를 따로 쓴다. 지금 동작, 바뀔 동작, 완료 조건(바뀌면 안 되는 것 포함)을 적고 같은 절차로 승인받는다. 변경을 다 만든 뒤에 원래 기획서에 반영한다.
- 기획서도 저장 기록에 함께 남긴다.

## 흔한 핑계와 실제
| 핑계 | 실제 |
|---|---|
| "간단해서 기획서가 필요 없다" | 긴 기획서는 필요 없어도 완료 조건은 필요하다. 두 줄이어도 된다. |
| "만들고 나서 정리하겠다" | 그건 설명서이지 기획서가 아니다. 기획서는 만들기 전에 써야 의미가 있다. |
| "회장님 뜻은 분명하다" | 분명한 요청에도 숨은 가정이 있다. 그 가정을 드러내는 것이 기획서다. |
| "좋은 생각이니 이번 판에 넣자" | 도중에 범위가 늘면 1판이 밀린다. 다음 판 후보에 적는다. |

## 마치기 전 확인
- [ ] 짐작한 것을 먼저 보여 드렸다
- [ ] 완료 조건이 구체적이고 확인 가능하다
- [ ] 지켜야 할 선(늘 한다 / 먼저 묻는다 / 하지 않는다)이 있다
- [ ] 목업으로 대신하는 것과 의도대로 안 되는 것을 맨 앞에 알렸다
- [ ] 화면 그림을 아티팩트로 드렸다
- [ ] 기획서를 파일로 저장했고, 승인을 받기 전에 차례를 끝냈다
