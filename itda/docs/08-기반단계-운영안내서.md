# 아이센스투게더 기반 단계 운영 안내서

> 읽는 사람: 회장님, 사내 전산 담당
> 기준: 「07-본제품개발계획서」의 「0. 기반」 단계, 중계 서버 0.2.0
> **이 문서의 가격·기간·사양 숫자는 모두 「예시」입니다.** 실제 값은 신청하거나 견적을 받을 때 각 회사 안내로 확인해야 합니다. 확인하지 못한 것을 확정처럼 적지 않았습니다.
> 서버를 띄우는 파일은 `itda/deploy/` 폴더에 있습니다(도커 설정, 환경 설정 견본, 캐디 설정).

## 먼저 알아 둘 사내 지침

- 회사 밖으로 나가는 공개 배포(외부 공개 링크, 외부 소비자에게 배포 등)는 **전략실의 사전 허락과 승인번호가 필요**합니다.
- 회사 계정이 소유하는 **비공개 서버 안에서 사내 구성원끼리 쓰는 운영은 제한이 없습니다.**
- 이 문서의 서버는 모두 회사 계정 소유의 비공개 서버를 전제로 합니다. 개인 계정으로 서버를 만들지 않습니다.

## 1. 회사 구글 클라우드에서 「데스크톱 앱」 로그인 열쇠 만들기

목적: 직원이 회사 구글 계정으로 로그인하고, 회사 도메인 밖의 계정은 못 들어오게 합니다.

1. 회사 구글 워크스페이스 관리자 계정으로 구글 클라우드 콘솔에 들어갑니다. 회사 조직 아래에 새 프로젝트를 만듭니다(이름 예시: 아이센스투게더).
2. 「API 및 서비스」 → 「OAuth 동의 화면」으로 갑니다.
3. 사용자 유형을 **「내부」** 로 고릅니다. 「내부」를 고르면 회사 도메인 계정만 로그인할 수 있습니다. (「외부」는 고르지 않습니다.)
4. 앱 이름(아이센스투게더), 지원 이메일, 개발자 연락처를 적고 저장합니다. 요청 범위는 기본 정보(이메일, 프로필)만 둡니다.
5. 「사용자 인증 정보」 → 「사용자 인증 정보 만들기」 → 「OAuth 클라이언트 ID」를 고릅니다.
6. 애플리케이션 유형을 **「데스크톱 앱」** 으로 하고 이름을 적어 만듭니다.
7. 화면에 나오는 **클라이언트 ID** 와 **클라이언트 보안 비밀**을 안전한 곳에 적어 둡니다. 보안 비밀은 메신저나 이메일로 보내지 않습니다.
8. 이 두 값을 3번 단계의 `.env` 파일에 넣습니다.
   - 클라이언트 ID → `TOGETHER_GOOGLE_CLIENT_ID`
   - 클라이언트 보안 비밀 → `TOGETHER_GOOGLE_CLIENT_SECRET`
   - 회사 도메인 → `TOGETHER_ALLOWED_DOMAIN`
9. 확인: 회사 계정으로 로그인되고, 회사 밖 계정(개인 지메일 등)으로는 거절되는지 시험합니다.

> 구글 콘솔 화면의 메뉴 이름은 구글이 바꿀 수 있습니다. 위 이름은 작성 시점 기준이며, 달라졌으면 같은 뜻의 메뉴를 찾아 주세요.

## 2. 클라우드 서버 한 대 준비하기 (후보 비교)

필요한 것: 리눅스 서버 한 대(도커 설치 가능), 고정 공인 주소, 회사 소유 도메인 이름 하나.
처음 개발팀 4명 규모라면 아래 사양이면 시작할 수 있다고 봅니다(예시): 중앙처리장치 2개, 메모리 4기가바이트, 디스크 50기가바이트.

| 후보 | 장점 | 확인할 점 | 월 비용 |
|---|---|---|---|
| 국내 클라우드(예: 네이버클라우드, 카카오클라우드, KT클라우드) | 한국어 지원, 국내 자료 보관, 세금계산서 처리 쉬움 | 도커 설치는 직접 해야 함, 가격표는 각 회사 확인 | 예시: 3만~8만 원 |
| 아마존 웹 서비스(서울 지역) | 자료와 사례가 많음, 백업·모니터링 도구가 풍부 | 영어 화면 위주, 요금 구조가 복잡 | 예시: 5만~12만 원 |
| 구글 클라우드(서울 지역) | 1번 단계와 같은 조직에서 관리 가능 | 요금 구조가 복잡 | 예시: 5만~12만 원 |
| 마이크로소프트 애저(한국 중부) | 회사가 이미 쓰고 있으면 계정 통합이 쉬움 | 같은 회사 계약 여부 확인 | 예시: 5만~12만 원 |

위 월 비용은 모두 **예시**이며 실제 견적이 아닙니다. 견적은 각 회사 요금 계산기로 따로 받아야 합니다.

**어느 것을 고르든 지킬 것**
1. 서버는 **회사 계정(admin@isens.camp 등 회사 소유 계정)** 으로 만들고, 개인 계정으로 만들지 않습니다.
2. 서버는 외부에 공개하는 서비스가 아니라 **회사 직원만 쓰는 비공개 운영**입니다. 접속은 회사 구글 계정 로그인으로만 허용됩니다.
3. 사내 지침상 회사 밖 공개 배포는 전략실 승인번호가 필요하고, 회사 계정 안의 비공개 운영은 제한이 없습니다. 협력사·외부 소비자에게 열 때가 오면 그 전에 전략실 허락을 먼저 받습니다.
4. 서버의 방화벽은 **80번, 443번만** 엽니다. 포스트그레스(5432번)는 바깥에 열지 않습니다. 이 묶음 설정도 포스트그레스를 바깥에 열지 않습니다.
5. 서버에 들어가는 관리자 계정은 최소 인원으로 하고 암호 대신 열쇠 파일 방식(보안 셸 열쇠)을 씁니다.

## 3. 도커로 띄우고 확인하기

서버에 도커와 도커 컴포즈가 설치되어 있어야 합니다.

1. 소스를 서버로 가져옵니다(회사 저장소에서 내려받기).
2. `itda/deploy` 폴더로 들어갑니다.
3. 설정 파일을 만듭니다: `cp .env.example .env`
4. `.env` 를 열어 빈칸을 채웁니다. 각 줄 위에 한국어 설명이 있습니다.
   - 반드시: `POSTGRES_PASSWORD`(길고 추측하기 어려운 글자)
   - 1번 단계 값: `TOGETHER_GOOGLE_CLIENT_ID`, `TOGETHER_GOOGLE_CLIENT_SECRET`, `TOGETHER_ALLOWED_DOMAIN`
   - 관리자: `TOGETHER_ADMINS`(4번 단계)
   - 선택: `ANTHROPIC_API_KEY`(AI 본부장 클로드를 켜려면)
5. 암호화(https·wss)를 처리하는 방법을 고릅니다.
   - **방법 가. 캐디 앞단(권장, 설정이 간단함)**: 회사 도메인(예: `together.회사도메인`)이 서버의 공인 주소를 가리키게 DNS 를 설정하고, `.env` 의 `TOGETHER_DOMAIN` 에 그 이름을 적습니다. 그다음 `docker compose --profile https up -d --build`. 인증서는 캐디가 자동으로 받고 갱신합니다.
   - **방법 나. 서버가 직접 암호화**: 회사가 따로 가진 인증서 파일을 쓸 때. 인증서 파일을 서버에 두고 중계 서버에 `--tls-cert`, `--tls-key` 옵션을 주어야 하는데, 이 묶음 설정은 그 경로를 아직 연결해 두지 않았습니다. 필요하면 개발팀에 요청해 주세요.
   - 암호화 없이 띄우면 사내망 시험용으로만 써야 합니다.
6. 띄우기: `docker compose up -d --build` (방법 가를 쓰면 위의 `--profile https` 명령). 첫 빌드는 오래 걸릴 수 있습니다(예시: 10~20분).
7. 상태 확인: `docker compose ps` 에서 중계 서버와 데이터베이스가 정상 상태인지 봅니다.
8. 건강 확인:
   - 서버 안에서: `curl http://127.0.0.1:7878/health`
   - 방법 가를 썼다면 밖에서: `https://회사도메인/health`
   - `"ok":true` 와 `"store":"postgres"` 가 나오면 정상입니다.
   - 로그인 방식(`"auth"`)이 `google` 로 나오는지도 봅니다. `open` 이면 구글 값이 비어 있다는 뜻이므로 `.env` 를 다시 확인합니다.
9. 데이터베이스 표는 서버가 처음 켜질 때 스스로 만듭니다. 따로 만들 필요가 없습니다.
10. 업데이트할 때: 새 소스를 받고 `docker compose up -d --build` 를 다시 실행합니다. 저장 공간(`db-data`)은 그대로 남습니다.

> 알림: 이 묶음 설정은 이 문서를 쓴 환경에서 도커 데몬을 켤 수 없어 **이미지 빌드까지는 확인하지 못했습니다.** 설정 파일의 문법 검사와, 중계 서버를 환경 변수만으로 켜서 `/health` 를 확인한 것까지만 했습니다. 서버에서 처음 띄울 때 오류가 나면 개발팀에 알려 주세요.

## 4. 관리자 지정과 퇴사자 차단

**관리자 지정**
1. `.env` 의 `TOGETHER_ADMINS` 에 관리자 이메일을 적습니다. 여러 명이면 쉼표로 나눕니다(예시: `a@회사도메인,b@회사도메인`).
2. 서버를 다시 시작합니다: `docker compose up -d`
3. 관리자는 계정 차단과 감사 기록 열람을 할 수 있습니다. 관리자 수는 최소로 합니다.

**퇴사자 차단 (아래 세 가지를 모두 합니다)**
1. **구글 워크스페이스에서 퇴사자 계정을 정지하거나 삭제합니다.** 이것이 가장 근본적인 차단입니다. 회사 계정이 없어지면 새 로그인은 되지 않습니다.
2. **중계 서버에서도 그 이메일을 차단합니다.** 관리자가 「이메일 차단」 요청을 보내면, 그 계정은 새로 들어올 수 없고 접속 중이면 바로 끊깁니다(해제도 가능). 한 번 차단하면 서버 기록에 남습니다.
   - 알림: 이 차단 요청은 서버에는 구현되어 있지만, **관리자용 화면 단추는 아직 확인되지 않았습니다.** 단추가 생기기 전까지는 개발팀이 대신 처리하거나, 화면 단추 추가를 개발팀에 요청해야 합니다.
3. **감사 기록 확인**: 관리자는 최근 활동 기록을 볼 수 있습니다. 퇴사 직전 활동이 걱정되면 이 기록을 확인합니다.

퇴사 절차 점검표에 위 1~2번을 넣어 두면 빠뜨리지 않습니다.

## 5. 백업(매일)과 되살리기

중요한 자료는 모두 포스트그레스에 있으므로, 데이터베이스를 매일 덤프로 떠 둡니다.

**매일 백업 설정**
1. 서버의 `itda/deploy/backup` 폴더가 데이터베이스 컨테이너의 `/backup` 과 연결되어 있습니다(묶음 설정에 포함).
2. 아래 명령을 매일 한 번 실행하도록 서버의 정기 실행(크론)에 넣습니다. 새벽 시간 예시:

   ```
   30 3 * * * cd /서버의/itda/deploy && docker compose exec -T db pg_dump -U together -Fc together > backup/together-$(date +\%F).dump
   ```

3. 오래된 백업 정리 예시(30일 보관): `find backup -name "*.dump" -mtime +30 -delete`
4. **서버 밖에도 사본을 둡니다.** 같은 서버에만 있으면 서버가 망가질 때 같이 사라집니다. 회사 계정의 별도 저장소(클라우드 저장소 등)에 복사합니다.
5. 월 1회는 되살리기 연습을 합니다. 되살려 보지 않은 백업은 믿을 수 없습니다.

**되살리기**
1. 서비스를 멈춥니다: `docker compose stop relay`
2. 새 데이터베이스에 덤프를 넣습니다:
   ```
   docker compose exec -T db pg_restore -U together -d together --clean --if-exists < backup/되살릴-파일.dump
   ```
3. 서비스를 켭니다: `docker compose start relay`
4. `/health` 로 확인하고, 앱에서 프로젝트가 보이는지 확인합니다.

## 6. 코드 서명 인증서와 자동 업데이트 준비물

**코드 서명이 필요한 이유**: 서명이 없는 설치 파일은 윈도우가 「알 수 없는 게시자」 경고를 띄우고, 보안 프로그램이 막을 수 있습니다. 직원에게 나눠 주려면 회사 이름으로 서명해야 합니다.

**무엇을 사야 하나**
- 윈도우용 **코드 서명 인증서**(회사 이름으로 발급). 종류는 크게 두 가지입니다.
  - 일반 인증서(OV): 가격이 낮고, 처음에는 경고가 남을 수 있음
  - 확장 검증 인증서(EV): 가격이 높고, 경고가 빨리 사라지는 편
- 최근에는 인증서 비밀 열쇠를 **보안 장치(하드웨어 토큰)나 클라우드 서명 서비스에 보관하도록 요구**하는 추세입니다. 구매 전에 판매처에 현재 규정을 확인해 주세요.
- 연 비용은 예시로 수십만 원대, 발급 기간은 예시로 영업일 기준 며칠~2주입니다. **둘 다 확정이 아니라 예시이며 판매처 견적으로 확인해야 합니다.**

**대략의 절차**
1. 인증서 판매처를 고릅니다(여러 곳 견적 비교).
2. 회사 서류를 준비합니다: 사업자등록증, 대표자 확인, 회사 대표 전화 확인 등(판매처마다 요구가 다름).
3. 신청하고 판매처의 회사 확인을 받습니다.
4. 인증서를 받습니다(보안 장치 또는 클라우드 서명 서비스 형태).
5. 개발팀이 설치 파일 만들기 과정에 서명 단계를 붙이고 시험합니다. 비밀 열쇠는 깃허브 작업 흐름의 보안 비밀 저장소 등 **회사 계정이 관리하는 곳**에만 둡니다.
6. 서명된 설치 파일을 시험 컴퓨터에서 열어 경고가 어떻게 뜨는지 확인합니다.

**자동 업데이트 준비물**
1. 업데이트 파일을 올려 둘 **회사 소유 저장소 주소**(비공개 서버나 회사 계정의 저장소)
2. 업데이트 파일 **서명용 열쇠 한 쌍**(코드 서명 인증서와는 별개로, 앱이 업데이트 파일이 진짜인지 확인하는 열쇠). 비밀 열쇠는 잃어버리면 이후 업데이트를 못 하므로 안전하게 보관합니다.
3. 새 판을 만들 때마다 올리는 절차와, 문제가 생기면 이전 판으로 되돌리는 절차
4. 위 저장소를 직원이 아니라 외부에도 열게 되면 사내 지침상 전략실 승인번호가 필요합니다.

> 알림: 자동 업데이트와 서명은 아직 만들어지지 않았고, 위는 준비물 안내입니다. 구체 작업은 개발 계획서의 「0. 기반」 단계 후반에 합니다.
